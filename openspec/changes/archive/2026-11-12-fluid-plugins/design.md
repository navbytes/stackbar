## Where the plugins live

Three options were weighed:

1. **This repository, `Plugins/`** (chosen). The plugins need protocol and
   host changes, so one pull request changes protocol, host, plugins and
   tests together, and one CI run (Linux, plus the self-hosted Mac) checks
   them. The plugins build as SwiftPM targets, so a protocol change that
   breaks one fails the build at once.
2. **A separate `fluid-plugins` repository.** The right home once FluidKit has
   tagged releases a plugin repository can pin to. Today every host change
   would need two coordinated pull requests with nothing pinning them
   together, and the plugins' CI would have to build Fluid from a branch.
3. **One repository per plugin.** Fine for third-party authors, who publish
   through signed bundles and an index; too much overhead for first-party
   plugins that move with the host.

Moving later is cheap: each plugin is one file, distribution already goes
through `.fluidplugin` bundles and `fluidctl index build`, and the app installs
from files, not from this layout.

`Examples/` stay small and teach one idea each. `Plugins/` are complete
utilities meant for daily use.

## The host owns the OS

Plugins run sandboxed and only talk to the host, so the host reads the OS for
them: AppKit for the clipboard and running apps, IOKit for power assertions and
battery, EventKit for the calendar (`Sources/Fluid/MacSystem.swift`). That
keeps plugins portable (they build and run on Linux against
`SimulatedSystem`), keeps TCC prompts to one app (Fluid) instead of one per
helper, and lets the host enforce capabilities and clean up: a plugin's power
assertion is released when it stops, crashes or is restarted, so a broken
plugin can't keep the Mac awake.

## Clipboard

- The supervisor polls the change count twice a second, only for plugins with
  a `.clipboard` trigger and the approved capability, and sends a
  `clipboard` trigger. The plugin reads the item with `Fluid.clipboard()`.
- Items marked `org.nspasteboard.ConcealedType`, `TransientType` or
  `AutoGeneratedType` come back as `concealed` with no content, so a password
  never reaches a plugin.
- Images are kept by the host as PNG files named by hash (newest 200), and
  plugins get an id. A plugin's 1 MB of storage holds only text and ids.
- `paste` writes the content, hides Fluid so the previous app is frontmost,
  and posts ⌘V. It needs Accessibility; without it the content is still
  copied and the call fails saying what to allow.

## Power

One assertion set per plugin (system idle sleep, plus display sleep when
asked), replaced on each call. The reason string is prefixed with the plugin's
name so `pmset -g assertions` shows who is holding it.

## Calendar

`calendarEvents` covers at most 31 days and 500 events, and cuts notes to 4000
characters. Access is requested on first use; an unbundled build (`swift run
Fluid`) has no Info.plist to ask with, so it fails with a message instead of
crashing.

## Hotkeys

`Manifest.hotkey` is parsed by `HotKeySpec` (shared, testable), and the app
registers it with Carbon (no Accessibility needed) to toggle the panel. It
needs cmd, ctrl or option so a plugin can't swallow plain typing.

## PR Cockpit

One GraphQL request fetches both searches with the head commit's check
rollup, review decision and mergeability, instead of a REST call per pull
request. It notifies on new review requests and on changes to your own PRs
(approved, changes requested, checks failing).
